## Tech Debt and Caveats

- **CFG-04 human-verify pending.** After milestone archive, the next time the user runs their DDNet server and issues `sv_map "<name-from-types>"`, it should load. If it doesn't, either: (a) `storage.cfg` was overwritten by DDNet between install and test, or (b) the DDNet version's storage engine doesn't recurse under added paths (unlikely based on upstream convention). Backup from `.ddnetcontrol-server-backup-*` and the simple 1-line config make this trivially debuggable.
- **TEST-01 external blocker.** Upstream testing feed has `Evening_Mist.map` returning 404. Our TEST-03 safety rail held in production across CLI, web, and native paths, so the feature is **safer** than if we had blindly downloaded what was available. When upstream fixes the URL, a rerun would positively demonstrate TEST-01.
- **Venv launcher on user's machine is broken** (exit 103). System Python fallback works. Documented in Phase 1 and 4. Not a sync-engine issue; it's a machine-config issue that the fallback chain transparently handles.

## Obsolete workarounds identified

The legacy `%APPDATA%\DDNet\add_maps.ps1` and `move_maps.ps1` scripts are now obsolete:

- `move_maps.ps1` flattened `types/*` into `maps/` — unnecessary after Phase 2 installed `storage.cfg` so the server reads from `types/` directly
- `add_maps.ps1` did `DELETE FROM record_maps; INSERT OR IGNORE (..., 'Unknown')` — the DELETE destroyed Player Points/Stars/Mapper. Phase 2's INSERT OR IGNORE preserves that metadata.

User may delete these files when convenient. The milestone does not delete them (user's filesystem, user's call).
